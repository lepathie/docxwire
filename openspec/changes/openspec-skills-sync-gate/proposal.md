# Proposal

## Why

The OpenSpec workflow skills in `.agents/skills/` are generated by the `@fission-ai/openspec` CLI (`openspec init` / `openspec update`), but nothing detects when the committed generated files fall behind the installed CLI version. Renovate updates the CLI package routinely (patches and dev-minors automerge), so the committed skills silently drift out of sync with the CLI they document. The natural fix — a Renovate post-upgrade task that runs `openspec update` — is not available: post-upgrade commands are blocked on the Mend-hosted Renovate app, and `allowedCommands` is a global-only option that a repository config cannot set. CI is therefore the enforcement point for this invariant.

## What Changes

- Add one step to the `openspec` job in `.github/workflows/ci.yaml`: run `openspec update --dry-run --json` and fail the job when the reported `changes` array is non-empty. The command exits 0 even while files are stale, so the step asserts on the JSON output rather than the exit code.
- No changes to application code, dependencies, or `renovate.json`.

## Capabilities

### New Capabilities

(None — tooling change, `skip_specs: true`)

### Modified Capabilities

(None)

## Impact

- `.github/workflows/ci.yaml` only: one new step in the existing `openspec` job, which already installs the npm dependencies and runs the OpenSpec CLI.
- Effect: any PR — including Renovate's own — that updates `@fission-ai/openspec` without regenerating the skills fails CI. The remedy is to run `openspec update` locally and commit the regenerated files (all `openspec-*/SKILL.md` files plus the `.agents/skills/.openspec-target` marker).
- Negligible runtime cost: one extra OpenSpec CLI invocation in the `openspec` job.
