# Proposal

## Why

The repo has no release process: `pyproject.toml` declares `0.1.0`, but there is no tag, no GitHub release, and no
changelog — cutting a release means manually bumping the version, re-stamping `uv.lock`, writing the notes, tagging, and
creating the release. The project already enforces Conventional Commits (commitlint), so the versioning information is
in the history; it just isn't wired up.

## What Changes

- Introduce [python-semantic-release (PSR)](https://python-semantic-release.readthedocs.io/) as the release tool: a
  GitHub Action on `main` computes the next version from the conventional commits since the last release tag and, in a
  single release commit, stamps `pyproject.toml` and `uv.lock`, updates `CHANGELOG.md`, creates the `v<version>` tag,
  and publishes a GitHub Release whose notes are the new changelog entry
- `CHANGELOG.md` is generated by PSR: with no tag history, the first release is cut manually (tag + GitHub release
  with the agreed notes), and from the second release on PSR maintains the file — its default init mode creates it
  from the git history, with the initial release masked to a one-line entry
- `pyproject.toml` gains a `[tool.semantic_release]` section (version declared in `project.version`, branch `main`),
  a `[tool.semantic_release.remote]` section (`ignore_token_for_push = true` — the token serves the Releases API,
  never the git push), and a `build` extra pinning `uv`, so the `build_command` can re-stamp `uv.lock` in the
  release commit — CI installs with `uv sync --frozen`, so the lockfile must stay consistent with the stamped version
- New `.github/workflows/release.yml` running the PSR **CLI** (via `uv run`) on pushes to `main`, with a concurrency
  guard and `contents: write` scoped to the release job. Because `main` is protected by a ruleset with required
  status checks, the release push must bypass it: the workflow checks out over SSH with a repository **deploy key**
  (a ruleset bypass actor) and runs PSR with that key in an `ssh-agent` — the Docker action can't see the agent
- One-time repository setup (user action): a deploy key with write access, the same key added to the `main`
  ruleset's bypass actors, and a `DEPLOY_KEY` repository secret holding the private key
- Standard SemVer versioning: `fix` bumps the patch, `feat` bumps the minor, a breaking change bumps the major — which
  PSR demotes to a minor bump while the major version is 0

Non-goals: publishing to PyPI (the tool is consumed from a checkout via `uv run`; the GitHub release is the distribution
surface), release asset uploads, re-publish/upsert behavior (`--force`), batch publishing.

## Capabilities

### New Capabilities

(None — tooling change; `skip_specs: true` in `.openspec.yaml`)

### Modified Capabilities

(None)

## Impact

- `pyproject.toml` — new `[tool.semantic_release]` and `[tool.semantic_release.remote]` sections plus a `build`
  optional-dependency extra (no runtime dependency change)
- `.github/workflows/release.yml` — new workflow, independent of the CI pipeline
- `CHANGELOG.md` — created by the release pipeline at the first automated release (no file in this change)
- GitHub repository settings — deploy key (write) + ruleset bypass actor + `DEPLOY_KEY` secret (one-time setup,
  outside the repo)
- No Python code, test, or CLI behavior changes; `make ci` is unaffected
